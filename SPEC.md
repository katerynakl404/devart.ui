# ui Package — Specification

## Project Structure

```
packages/ui/
├── src/components/          — 46 component directories; each `<Name>/index.tsx` is the public entry, with co-located parts, `constants.ts`, `types.ts`, `*.stories.tsx`
├── src/hooks/               — `use-mobile.tsx` (exported); `use-autocomplete/`, `use-scroll-shadow/` (internal, reachable only through their components)
├── src/lib/                 — `utils.ts` (`cn`), `constants.ts` (`THEME_COLORS`), `breakpoints.ts` (`BREAKPOINTS` — one source for `screens`, `--breakpoint-*` and the JS media queries)
├── src/tailwind-preset.ts   — the Tailwind v3 preset consuming apps spread in (`theme.extend`, the `pressed:` variant plugin, `tailwindcss-animate`) plus `contentGlobs` (absolute globs into the package's `src`/`dist`, since v3 presets can't carry `content`)
├── globals.css              — pure CSS-variable token system (`:root` + `.dark`) only; no `@tailwind` directives and no `@layer` block — the consumer owns Tailwind's own layers
├── tailwind.config.ts       — thin local config wrapping the preset; Storybook-only, not consumed by apps
├── tsconfig.base.json       — vendored TS config (was `@insightis/typescript-config`); package is self-contained
├── vitest.config.ts         — local vitest config (was `@insightis/unit-tests`); `passWithNoTests` until unit tests land
├── .npmignore               — forces npm to ignore `.gitignore` so a future `dist` ignore cannot drop the build from the tarball
├── fonts.css, fonts/        — self-hosted DM Sans `@font-face` rules plus the four `.woff2` files
├── .storybook/              — Storybook 10 (`@storybook/react-vite`); `tailwind.css` (the `@tailwind` directives) + `../globals.css` + `../fonts.css` + `preview.css`, all loaded from `preview.tsx`
└── README.md                — usage guide (imports, catalog, `cn`/`cva` recipes)
```

---

## Concept

**ui** (`@devart/ui-react`) is the design-system package: 45 presentational primitives over 16 Radix primitives, `sonner`, `react-day-picker` and `react-resizable-panels`, all styled exclusively through CVA recipes over CSS-variable design tokens. It owns the token system and the Tailwind theme that consuming apps inherit. It holds no server state, no routing, no i18n and no domain knowledge — feature-specific compositions belong in `apps/web`. Usage recipes: `README.md`.

## Package Surface

Subpath-only. `exports` declares no `"."` entry, so `import { Button } from '@devart/ui-react'` is not merely discouraged — it does not resolve.

| Subpath | Target |
|---|---|
| `./tailwind-preset` | `src/tailwind-preset.ts` — exports `preset` and `contentGlobs` |
| `./globals.css` | `globals.css` |
| `./fonts.css` | `fonts.css` |
| `./palettes.css` | `palettes.css` — the colour packs, generated by `scripts/gen-palettes.mjs` |
| `./package.json` | `package.json` |
| `./cn` | `src/lib/utils.ts` |
| `./use-mobile` | `src/hooks/use-mobile.tsx` (`useIsMobile`, `useMaxWidth`, `BREAKPOINTS`) |
| `./*` | `src/components/*/index.tsx` |

Wildcard = component API; `use-autocomplete` / `use-scroll-shadow` stay private. Component/`cn`/`use-mobile` entries carry `source` (Vite dev) + `types`/`default` → `dist` (`tsc` then `tsc-alias` adds `.js` / `/index.js`). Source stays Bundler + extensionless relatives. Bare-specifier exceptions in source: `tailwindcss/defaultTheme.js` / `plugin.js` (no package `exports`; `tsc-alias` skips bare imports).

`./tailwind-preset` local export → `./src/tailwind-preset.ts` so Tailwind jiti (and `pnpm dev`) needs no ui build; relatives stay extensionless — jiti resolves `.ts`. `publishConfig` still ships `dist` (with `tsc-alias` rewrites). `contentGlobs` resolves package root from `import.meta.url` either way.

Publishing swaps the map: `publishConfig.exports` restates the same keys with the `source` condition dropped (the tarball ships no `src/`), which is why the preset lives under `src/` rather than at the package root. `publishConfig` also sets `access: "restricted"` and the GitLab Package Registry of `devart/components/devart.ui.react`. `files` is an explicit allowlist — `dist`, `globals.css`, `fonts.css`, `fonts`, `LICENSE`, `README.md` — so `src/`, `.storybook/`, `storybook-static/`, `.turbo/`, and local configs stay out of the tarball. A package-local `.npmignore` exists so npm does not fall through to `.gitignore`: the repo-root `.gitignore` that ignores `dist` sits outside the package directory (npm never sees it), and a future package-local `.gitignore` that also ignored `dist` would quietly drop the built output from the tarball. The incremental build cache is written to `.tsbuildinfo` at the package root so it stays out of the tarball, and the `build` script deletes it alongside `dist` so a wiped `dist` can never be mistaken for an up-to-date project. `scripts/verify-dist.mjs` runs after `tsc` and `tsc-alias` and gates all of it in a plain Node process: every entry point must import *by package specifier*, no `@/` alias or self-reference may survive into the output, the two export maps must mirror each other key for key with every target present on disk, the shipped `.d.ts` files must type-check standalone (`tsconfig.dist-check.json`), and `npm pack --dry-run` must list every `publishConfig` target while excluding the developer surface, under a 2 MB size budget.

## Design Tokens

**Design System v2 is the only token system.** The redesign originally froze the pre-v2 palette alongside it so components could migrate one ticket at a time (see decision 2); that migration is complete and the frozen block has been deleted outright from both `globals.css` and `THEME_COLORS` — there is no legacy holdout left to avoid.

### Design System v2

Three color layers, plus a small geometry/elevation/typography set; 307 custom-property declarations in total:

0. **Geometry, elevation, typography** (theme-independent, `:root` only) — `--radius-sm/--radius/--radius-md/--radius-lg/--radius-xl` (seeded with Tailwind's own default values), `--sidebar-width/--sidebar-width-icon/--sidebar-width-mobile`, `--shadow-thumb/--shadow-thumb-hover`, `--font-sans`, `--font-size-{xxs,xs,compact,sm,base,lg,xl,2xl,3xl,4xl}` and `--line-height-{xs,sm,base,lg,xl,2xl,3xl,4xl}` (same Tailwind-default seeding as the radii; `xxs`/`compact` carry no paired line-height), the `--tint-{4,5,6,8,10,12,15,20,25,30,40,55,80}` overlay-strength scale, and `--font-weight-{light,normal,medium,semibold,bold,extrabold,black}` (also seeded at Tailwind's own defaults; `thin`/`extralight` omitted as unused). Surfaced through `tailwind-preset.ts`, not `THEME_COLORS`. `--breakpoint-{sm,md,lg,xl}` belong to this group too but are the one token the CSS files do not declare — the preset emits them into Tailwind's base layer from `BREAKPOINTS`, so they cannot disagree with `screens` (decision 9).
1. **Primitives** — `--brand-*`, `--tertiary-*`, `--slate-*`, `--grey-*`, `--red-*`, `--orange-500`, `--green-*`, `--chart-{teal,orange,violet,blue}-*`. Theme-independent, and deliberately **not** exposed to Tailwind.
2. **Semantic** — `--surface-{page,card,card2,chips,accent}`, `--brand-{primary,secondary,tertiary,hover,press}`, `--ink-{primary,body,secondary,inactive,highlight}`, `--stroke-border{,-hover}`, `--state-{overlay,hover,pressed,disabled,focus-ring}`, `--fb-*` (feedback), `--logo-*`, `--mx-group-band`, `--chat-{shell-bg,glow-fill}`, `--overlay-scrim`, and `--chart-*` (axis, grid, surface and the six series).
3. **Component-scoped** — `--btn-*`, `--badge-*`, `--switch-*`, `--toast-*`, `--segctrl-{btn-hover-bg,hover-shadow,active-shadow}`, `--tbl-*`, `--dropzone-*`, `--card-border-*`, `--banner-{grad-*,ic-shadow}`, `--plan-card-featured-{bg,border,shadow}`, `--shadow-{rest,card-hover,lift-hover,overlay-soft,menu,dropdown}`, `--input-{focus,error}`, `--field-border-hover`, `--icon-wrapper-bg`, `--content-on-solid`, `--focus-ring-brand`.

Layers 2 and 3 are surfaced by `THEME_COLORS` (`src/lib/constants.ts`) into `theme.extend.colors`, with two exceptions: the `--chart-*` tokens, which no class reads — they are declared in both themes purely so a consumer can pull them out of computed styles — and the shadow/gradient tokens, which the preset surfaces under `boxShadow` / `backgroundImage` rather than `colors`. Non-obvious points:

- **`<alpha-value>` vs bare `var()`** — HSL-triplet tokens are wrapped `hsl(var(--x) / <alpha-value>)`, which is what makes `bg-brand-primary/[0.06]` work. `color-mix()` tokens are passed through as bare `var(...)` and accept **no** alpha modifier — an `hsl()` wrapper around them would emit invalid CSS. Current bare-`var()` keys (`src/lib/constants.ts`): `--btn-secondary-bg-hover`, `--btn-outline-bg-hover`, `--btn-outline-bg-press`, `--btn-outline-destructive-bg-hover`, `--btn-outline-destructive-bg-press`, `--badge-brand-{bg,border,text}`, `--badge-green-{bg,border,text}`, `--toast-bg-*`, `--toast-border-*`, `--segctrl-btn-hover-bg`, `--state-{hover,pressed}`, `--tbl-row-{hover,pressed}`, `--icon-wrapper-bg`, `--card-border-{hover,press}`, `--card-lift-border`, `--plan-card-featured-border`, `--dropzone-border-active`, `--dropzone-bg-active`, `--banner-grad-sub`, `--banner-grad-ic-{bg,border,shadow}`, `--overlay-scrim`.
- **Interaction states are relative overlays, and two of them share a strength** —
  `--state-hover`, `--state-pressed`, `--tbl-row-hover` and `--tbl-row-pressed` are
  `color-mix(… <base> <tint>, transparent)` washes over `--state-overlay`
  (`--brand-300` on light, `--slate-400` on dark — a coloured wash over the
  near-black card reads as a cast rather than a lift). One set of percentages —
  4 / 8 / 8 / 12 — serves both themes, because `--slate-400` moves against the
  dark card at roughly the rate `--brand-300` moves against white.

  `--tbl-row-pressed` and `--state-hover` therefore resolve to the **same
  declaration**, and that is deliberate rather than the collision it would have
  been before: overlays composite instead of replacing, so a control hovering on
  a selected row lands at 8% over 8% ≈ 15% and reads a clear step deeper
  (`#F0F8F9` → `#E3F1F4` on light, `#21222A` → `#2A2C36` on dark). A check that
  asserts the four raw values are distinct is therefore testing the wrong thing —
  the defect lives in the composite, not in the declaration.

  Two consequences: where a **solid** colour is needed (a gradient that must end
  opaque, anything masking text) pre-composite the same wash over the surface
  rather than reaching for a state token; and `--state-disabled` stays an opaque
  fill, because it is a rest surface that never stacks on another state.
- **Nested keys flatten with a hyphen and casing is significant** — `stroke.DEFAULT` → `border-stroke`, `outlineDestructive.border` → `border-outlineDestructive-border`.
- **Duplicate aliases** — `table.row-hover` and `tbl.row-hover` (likewise `-row-pressed`) both point at the same `--tbl-*` variables.
- **Table row states are utilities on `TableCell`, not row CSS** — the former `@layer components` block keyed off `[data-slot="table-row"][data-interactive]` is gone; `globals.css` carries no component-layer CSS at all now. `TableRow` (`src/components/Table/TableRow.tsx`) stamps `group/row` on the `<tr>`, and `TableCell` (`TableCell.tsx`) carries the fill utilities — `group-data-[interactive]/row:group-hover/row:bg-tbl-row-hover`, `…:group-active/row:bg-tbl-row-pressed`, `group-[.is-selected]/row:bg-tbl-row-pressed` — so the paint lands on every `<td>` rather than on the row. The `data-interactive` attribute and `.is-selected` class contract on the row is unchanged; only where the styles live moved. Hover and press *while selected* both resolve to `--tbl-row-pressed` and both carry `!important`, because Tailwind emits the `.is-selected` variant classes before the `data-interactive` ones in the generated stylesheet, so a plain-interactive rule of equal specificity would otherwise win and the selection would visibly disappear under the pointer. There is no separate selected+hover colour: a selected row keeps its own surface, and the controls on it composite on top of it.

### Layer Responsibilities

| Layer | Answers | Declared in | `.dark` counterpart | Exposed to Tailwind |
|---|---|---|---|---|
| 1 — Primitives | *what colour exists* | `:root` only | never | never (decision 3) |
| 2 — Semantic | *what role it plays* | `:root` + `.dark` | when the role changes hue | `THEME_COLORS` |
| 3 — Component | *how one control paints in one state* | `:root` + `.dark` | only if pinned to Layer 1 | `THEME_COLORS` |
| Non-colour | radius, shadow, motion, type | `:root` only | never | `tailwind-preset.ts` |

A Layer-1 value is a bare HSL triplet with the hex in a trailing comment
(`--brand-600: 179 89.6% 26.5%; /* #07807E */`). Every higher layer aliases it
**as a triplet** — `--surface-page: var(--slate-50)` — never as `hsl(...)`, because the
`hsl(var(--x) / <alpha-value>)` wrapper in `THEME_COLORS` supplies the function.
The only place `hsl()` appears inside a declaration is within `color-mix()`,
which needs a real colour, not a triplet.

**The dark-mode rule follows from that indirection.** A token needs a `.dark`
re-declaration only when it pins a Layer-1 ramp step; one that references a
Layer-2 role re-resolves for free. `Badge` shows both halves:

```css
--badge-primary-bg: var(--brand-50);          /* Layer 1 -> needs a .dark twin */
--badge-primary-text: var(--brand-secondary); /* Layer 2 -> no .dark twin      */
```

That is why `:root` carries 231 declarations and `.dark` only 76.

### Adding a Token

Work down the list and stop at the first branch that fits.

1. **Can an existing semantic token carry it with an alpha modifier?** Then add
   no token. `Badge`'s `attention` / `success` / `error` variants are
   `bg-fb-attention/15`, `bg-fb-green/15`, `bg-fb-red/15` — three visual
   treatments, zero new variables.
2. **Is it a new *role* several components will reach for?** Layer 2. Declare it
   in `:root` against a Layer-1 step, add a `.dark` line, expose it in
   `THEME_COLORS`.
3. **Is it one control in one state?** Layer 3, named `--<component>-<part>-<state>`
   (`--btn-outline-bg-press`, `--switch-off-bg-hover`, `--tbl-row-pressed`).
4. **Is it not a colour?** Skip `THEME_COLORS` entirely — it goes in the preset
   under the matching `theme.extend` key (table below).
5. **Does only JS read it?** Declare it in both themes and expose it nowhere; the
   chart palette (`--chart-series-1..6`, `--chart-axis-*`, `--chart-grid`,
   `--chart-surface`) is the whole of this category today. Consumers read it out
   of computed styles, so it must never be dropped for being "unused".
6. **Is the shade genuinely absent from the ramps?** Only then add a Layer-1
   primitive — and it stays out of `THEME_COLORS`.

Non-colour axes never touch `src/lib/constants.ts`:

| Token prefix | Preset key | Class |
|---|---|---|
| `--radius-*` | `borderRadius` | `rounded-md` |
| `--shadow-*`, `--segctrl-*-shadow`, `--*-ic-shadow` | `boxShadow` | `shadow-menu` |
| `--motion-*` | `transitionDuration` | `duration-fast` |
| `--font-size-*` / `--line-height-*` | `fontSize` | `text-sm` |
| `--font-weight-*` | `fontWeight` | `font-semibold` |
| `--font-sans` | `fontFamily` | `font-sans` |
| `--opacity-disabled` | `opacity` | `opacity-disabled` |
| `--chat-*`, `--banner-grad-*`, `--plan-card-featured-bg` | `backgroundImage` | `bg-chat-shell` |
| `--sidebar-width*` | *(none)* | read as `var()` in a `style` prop |

### Token Worked Examples

**A — new semantic role (Layer 2).** An "info" feedback colour, blue in both
themes but a different step each:

```css
/* globals.css, :root, Layer 2 block */
--fb-info: var(--chart-blue-600);   /* #2F6FC0 */
/* globals.css, .dark, Layer 2 block */
--fb-info: var(--chart-blue-500);   /* #4784D6 — lifted for AA on dark */
```
```ts
// src/lib/constants.ts
fb: { /* … */ info: 'hsl(var(--fb-info) / <alpha-value>)' },
```

Now `text-fb-info` and `bg-fb-info/15` both work, and no component knows the theme.

**B — opaque tint (Layer 3, `color-mix`).** A tint that sits over a card border
cannot be an alpha fill, or the border shows through — this is exactly why
`--badge-brand-bg` exists instead of `bg-brand-primary/22`:

```css
--badge-brand-bg: color-mix(in srgb, hsl(var(--brand-primary)) 22%, hsl(var(--surface-card)));
```
```ts
'brand-bg': 'var(--badge-brand-bg)',   // bare var — NOT hsl(...)
```

Both operands are Layer-2 roles, so the mix re-resolves per theme with no `.dark`
line. The cost is fixed: `bg-badge-brand-bg/50` is silently dead — a `color-mix()`
token takes no alpha modifier, ever.

Re-declare such a token in `.dark` only to change the *ratio*, not the operands —
`--toast-bg-success` mixes 5% on light and 8% on dark, because the same percentage
reads weaker against a dark card.

**C — non-colour axis.** A new elevation:

```css
--shadow-popover: 0 4px 12px -2px rgb(0 0 0 / 10%);
```
```ts
// tailwind-preset.ts -> theme.extend.boxShadow
'popover': 'var(--shadow-popover)',
```

Nothing in `THEME_COLORS`; the class is `shadow-popover`.

### Token Invariants and Failure Modes

Nothing in the build checks any of these — every violation surfaces as a wrong
pixel, never as an error (decision 10).

- **A class naming a key absent from `THEME_COLORS` generates no CSS.** A typo in
  a token name is invisible.
- **A token declared only in `.dark` paints nothing in light mode.** Two exist
  today — `--fb-red-hover` and `--fb-red-press` — each carrying a `declared on
  dark only` comment. Both are exposed in `THEME_COLORS` and neither is used by
  any component, which is the only reason the gap is harmless. Adding a third
  without a `:root` value is a light-mode bug. (`--border-hover` used to be a
  third; it was dark-only, exposed as `stroke-border-hover`, and read by nothing
  — so it was removed rather than completed.)
- **`hsl()` around a `color-mix()` token emits invalid CSS** and the declaration is
  dropped whole.
- **A tint carries its strength as a token, a blend carries a literal.** The two
  look alike and are not the same thing:

  | | shape | strength |
  |---|---|---|
  | **Tint** — a wash of one colour over nothing | `color-mix(in srgb, hsl(var(--x)) var(--tint-N), transparent)` | one of the 12 `--tint-*` steps, never a literal |
  | **Blend** — a ratio between two opaque colours | `color-mix(in srgb, hsl(var(--x)) 22%, hsl(var(--y)))` | a literal, because it is a mix ratio and not an overlay strength |

  Snapping a blend onto the tint scale is a category error: `--segctrl-btn-hover-bg`
  is the 50% midpoint between two surfaces, and 50% is the meaning, not a strength.
  Shadow alphas and gradient stops keep literals for the same reason. The scale
  exists so that "how strong does every wash read" is one edit; there are 23 tints
  on it today, and 25 blends plus 12 shadow/gradient stops deliberately off it.
- **An exposed token with no call site drifts.** `--overlay-scrim` is exposed as
  `bg-overlay-scrim`, but `ModalOverlay` and `Sheet` still hardcode `bg-black/80`,
  so the token is unreachable and the scrim is not themeable.
- **Every token edit is a two-file edit** — `globals.css` and the consumer's own
  copy (`apps/web/src/index.css`); see Cross-Feature Dependencies. Per
  `CONTRIBUTING.md` a `globals.css` change is at least a **minor** bump, and
  `check-changeset` enforces that for `globals.css`, `src/lib/constants.ts` and
  `src/lib/breakpoints.ts`.

## Component Conventions

- **CVA is the single source of variant truth** — 43 `cva()` definitions; the variants object is exported next to the component (`buttonVariants`, `badgeVariants`, `cardVariants`, `iconButtonVariants`, `bannerVariants`, …) so consumers can reuse classes without rendering. Base strings are themselves composed with `cn()`, one concern per line. `Toast` deliberately opts out — Sonner renders imperatively from a plain options object, so its variant styling lives in string maps (`VARIANT_COLOR_MAP`, `VARIANT_BG_MAP`, `VARIANT_BORDER_MAP` in `Toast/ToastMessage/constants.ts`).
- **The style discriminator prop is always `variant`, never `tone`** — where a variant must be reachable from CSS it is mirrored onto `data-variant` (`Sidebar`), and structural parts carry `data-slot` (47 occurrences across 25 files).
- **One DOM marker is a behavioural contract, not styling** — `ModalOverlay` and `SheetOverlay` both stamp a bare `data-modal-overlay`, so a consumer can answer *"is any modal open?"* with a single selector (`[data-modal-overlay][data-state="open"]`, Radix supplying `data-state`) instead of reading every modal store. No CSS in the package targets it. A new overlay-backed primitive must stamp the same attribute, and removing it from either overlay changes consumer behaviour with nothing failing — see Cross-Feature Dependencies.
- **`pressed:` instead of `active:`** — see decision 6. Applied in `Button` and `IconButton` recipes and by two `apps/web` rows.
- **No `forwardRef`** — React 19; `ref` is an ordinary prop declared on the props interface (`ref?: Ref<HTMLButtonElement>`).
- **Radix composition** — Radix-backed components re-export named parts from `index.tsx` (`Modal` exports 10; `Sidebar` exports 16 parts plus `useSidebar` and two type guards). `asChild` + `Slot` is the only sanctioned way to change the rendered element.
- **Extend before adding** — a new visual treatment is a new variant on the existing primitive; a genuinely new primitive gets a directory under `src/components/`. `Button` and `IconButton` share one variant scale (12 and 9 variants respectively) by convention, not by code.
- **Loading is not disabling** — `isLoading` on `Button`/`IconButton` swaps content for `Spinner`, sets `aria-busy`, and blocks interaction with `pointer-events-none opacity-disabled` while keeping the variant fill; it never toggles `disabled`, which would drop the control out of the tab order.
- **`cn()` only** — `twMerge` is extended with a `font-size` class group covering `text-xxs`.

## Theming

One mechanism: `.dark` re-declares the same variable names, so every token is theme-resolved by the cascade and no component reads a theme value in JS. `apps/web`'s `ThemeProvider` toggles `dark` on `document.documentElement` for `light | dark | system`; because the tokens are plain cascade, a scoped `.dark` also works — `AuthPageLayout` puts `dark` in its own `className` to force dark auth pages regardless of user preference. Storybook flips the same class via `withThemeByClassName` (`light: ''`, `dark: 'dark'`). Eight tokens are theme-independent by design — `--btn-primary-{bg,bg-hover,bg-press,text}`, `--content-on-solid`, `--focus-ring-brand`, `--banner-grad-{text,sub}` — pinned to a Layer-1 step in `:root` with no `.dark` counterpart, so a primary button stays brand-teal with white text in both themes. Five further tokens (`--fb-red`, `--fb-error-{hover,press}`, `--fb-attention`, `--banner-grad-btn-text`) *are* re-declared in `.dark`, but with the identical value — no-op overrides kept for symmetry with their neighbours. `--btn-outline-destructive-border{,-hover}` used to sit in that list; they are now genuinely theme-aware (light Red-700/Red-800, dark Red-400/Red-300), because on a near-black Card the light pair inverted the hover step — contrast fell 2.76 to 2.15 instead of rising. The single place token values are mirrored into TypeScript is `apps/web/src/shared/utils/chart/chart-palette-fallback.ts`, a fallback for the chart palette that is normally read out of computed styles by briefly toggling `.dark` (`with-resolved-theme.ts`).

Sidebar widths, border radii, the thumb shadow pair, the font family, the type scale, the font weights, the motion durations and the disabled opacity follow the same cascade mechanism but are theme-independent (`:root` only, no `.dark` counterpart): `--sidebar-width*`, `--radius-*`, `--shadow-thumb*`, `--font-sans`, `--font-size-*`, `--line-height-*`, `--font-weight-*`, `--motion-{fast,base,slow}`, `--opacity-disabled`. Overriding any of them is a plain `:root { --x: … }` redeclaration or a `style` prop — there is no dark-mode value to keep in sync. `--breakpoint-*` are `:root`-only as well, but the preset generates them and redeclaring one changes nothing (decision 9).

### Creating a New Theme

A theme in this package is a CSS class that re-declares a subset of Layer 2 and
Layer 3. There is no theme provider, no context and no JS branch inside the
package — `.dark` is the reference implementation and the only one shipped.

Its shape is the budget for any new theme: **78 declarations — 76 overrides of a
`:root` token plus 2 declared only there** (`--fb-red-hover`, `--fb-red-press`).
Nine of the 76 repeat the `:root` value verbatim, so the real delta between the
two shipped themes is **67 values**.
Layer 1 and the geometry/typography/motion set are never re-declared in a theme
block.

Three shapes, in rising cost:

| Goal | Mechanism | Touches the package? |
|---|---|---|
| Re-skin light or dark | redeclare tokens in your own `:root` / `.dark` after the `@import` | no |
| Add a third theme | a new class block (`.midnight { … }`) toggled like `dark` | no, unless you hit the two holdouts below |
| Theme one subtree | the same class on a wrapper element | no — but see Portals |

#### What a third theme must re-declare

Start from the 43 Layer-2 tokens `.dark` touches — `--surface-*`,
`--ink-*`, `--brand-*`, `--stroke-*`, `--state-*`, `--fb-*`, `--logo-*`,
`--chart-series-*`, `--chat-*`, `--overlay-scrim`. Most of Layer 3 then follows
for free: of the 118 Layer-2/3 tokens declared in `:root`, `.dark` leaves 46
alone precisely because they reference Layer-2 roles or `color-mix()` over them.

Add a Layer-3 override only for the two reasons `.dark` does:

- the token pins a Layer-1 ramp step — `--badge-primary-bg: var(--brand-50)`
  needs `var(--brand-800)` on dark;
- the *ratio* of a `color-mix()` reads wrong — `--toast-bg-success` mixes 5% on
  light and 8% on dark with identical operands.

**Eight tokens will not follow your theme, by design.** They are pinned to Layer 1
with no `.dark` counterpart, so they render identically in every theme:

```
--btn-primary-bg        --btn-primary-bg-hover    --btn-primary-bg-press
--btn-primary-text      --content-on-solid        --focus-ring-brand
--banner-grad-text      --banner-grad-sub
```

A primary button is brand-teal with white text in both shipped themes, and the
focus ring is `--brand-600` in both. A theme that changes the brand hue, or that
needs a dark fill on a light-inked control, must re-declare these explicitly —
nothing else will.

### Colour packs

A **pack** is the cheapest kind of re-skin the system has, and it is not a theme:
it redeclares **Layer 1 only** — the `--brand-*` and `--tertiary-*` ramps — and
nothing above them. Semantic roles and component tokens reach the primitives
through `var()`, so every one of them re-resolves by itself, including each
`color-mix()` recipe: button hover fills, card borders, toast tints, banner
gradients, the pale fills behind a selected row or a pressed chip.

That is decision 3 paying for itself. No component can name a ramp step, so no
component has to be touched to change the colour of the whole system.

```css
@import '@devart/ui-react/globals.css';
@import '@devart/ui-react/palettes.css';   /* after, always */
```
```html
<html data-palette="iris">
```

Four packs ship — `azure`, `blue`, `indigo`, `iris` — and no attribute leaves
the system on its own teal, which the file does not declare.
`:root[data-palette]` (0,2,0) beats `:root` and `.dark` (0,1,0), and
`:root[data-palette].dark` (0,3,0) beats the dark branch, so a pack needs no
`!important` and no load-order luck beyond coming second.

Every pack takes the L and C profile of the default teal (C ≈ 0.09 in OKLCH) and
rotates the hue only, so no pack is louder than teal; the key steps are solved
against contrast thresholds taken from the teal original. Feedback colours are
deliberately not packed — red and attention stay loud, because that is their job.

A pack is primitives only on purpose. Splitting the half-tones apart — a neutral
sidebar with a brand chip — means touching a semantic token or hanging a rule
off a compiled Tailwind class name, and such a rule survives until the next
build. A half-tone that reads badly is a reason to fix the system, not the pack.

`palettes.css` is generated: edit `scripts/gen-palettes.mjs` and run
`pnpm gen-palettes`. Storybook carries a **Palette** toolbar switch, which is the
only way to see that a component reads roles rather than shades — one that
pinned itself to a ramp step stays teal while the page around it moves.

#### The two class-level holdouts

The package branches on the theme in a class string — rather than through a
token — in exactly two places:

- `src/components/Datepicker/CalendarDayButton.tsx` — `dark:hover:text-ink-primary`
- `src/components/SegmentedControl/SegmentedControlTrigger.tsx` — `dark:data-[state=active]:bg-surface-chips`

Under a third theme class these fall back to their light-mode rule: a
`SegmentedControl`'s active pill would paint `--surface-card` instead of
`--surface-chips`, and on a dark-like theme the raised pill stops reading as
raised. Three ways out, best first:

1. **Tokenize it** — introduce `--segctrl-active-bg` (Layer 3, `--surface-card`
   on `:root`, `--surface-chips` on `.dark`) and drop the `dark:` class. This is
   what decision 4 exists for, and it makes the component theme-count-agnostic.
2. **Ship both classes** — apply `class="dark midnight"`, letting `.midnight`
   win the cascade on the tokens it redeclares while `dark:` rules still fire.
3. **Widen the variant** in your own config (Tailwind >= 3.4.1; peer range is `^3.4`):
   ```ts
   darkMode: ['variant', ['.dark &', '.midnight &']],
   ```

#### Tailwind config side

The preset hardcodes `darkMode: ['class']`. A consumer's own top-level `darkMode`
**replaces** it rather than merging — v3 presets merge `theme` and `plugins`, not
arbitrary top-level keys. A third theme that never needs `dark:` utilities
requires no Tailwind change at all: every component reads tokens, so the cascade
alone re-themes it.

#### Portals

Nine components render through a portal to `document.body` — `Modal`, `Sheet`,
`Popover`, `DropdownMenu`, `Tooltip`, `TruncatedTitleTooltip` — as does Sonner's
`Toaster`. A theme class on a subtree does not reach them: a dialog opened from
inside a scoped theme renders under whatever class the document root carries.
Scoped theming is therefore safe for page chrome and unsafe for any surface that
opens a portaled overlay, unless the same class is also on `<html>`.

#### Not themeable

`--radius-*`, `--sidebar-width*`, `--shadow-thumb*`, `--font-sans`,
`--font-size-*`, `--line-height-*`, `--font-weight-*`, `--motion-*` and
`--opacity-disabled` are `:root`-only and theme-independent; override them once
globally rather than per theme. `--breakpoint-*` are inert (decision 9) — a theme
block redeclaring one changes nothing.

#### Checklist

1. Declare the class block after the `@import` of `globals.css`, never inside it.
2. Cover the 44 Layer-2 roles; add Layer 3 only for ramp-pinned tokens and mix ratios.
3. Decide explicitly about the 8 theme-constant tokens above.
4. Handle the two `dark:` holdouts.
5. Verify in Storybook by adding the theme to `withThemeByClassName` in
   `.storybook/preview.tsx` — this is the only gate the package has (decision 10);
   a token you forget produces an unstyled element, not an error.
6. Open one portaled surface (`Modal`) under the theme to confirm the class is on
   the document root and not only on a wrapper.

#### Worked example — a `.midnight` third theme

```css
@import '@devart/ui-react/globals.css';

.midnight {
  /* Layer 2 — the 43 roles; abbreviated */
  --surface-page: 258 30% 6%;
  --surface-card: 257 26% 11%;
  --surface-card2: 257 24% 15%;
  --surface-chips: 257 22% 19%;
  --ink-primary: 250 20% 97%;
  --ink-body: 250 14% 88%;
  --ink-secondary: 250 10% 70%;
  --stroke-border: 257 20% 22%;
  --state-hover: 257 24% 15%;
  /* … */

  /* The 8 constants — opted into the theme rather than inherited */
  --btn-primary-bg: var(--tertiary-500);
  --btn-primary-text: var(--grey-950);
  --focus-ring-brand: var(--tertiary-400);

  /* Layer 3 — only what the roles cannot carry */
  --badge-primary-bg: 257 24% 19%;   /* was pinned to --brand-50 */
  --toast-bg-success: color-mix(in srgb, hsl(var(--fb-green)) 8%, hsl(var(--surface-card)));
}
```
```ts
// tailwind.config.ts — only needed to keep the two dark: holdouts working
darkMode: ['variant', ['.dark &', '.midnight &']],
```

Everything else — all 43 `cva()` recipes, every `color-mix()` tint, both Layer-1
ramps — is untouched.

## Types

`VariantProps<typeof xVariants>` intersected with the DOM props type is the standard props shape (`ButtonProps`, `BadgeProps extends HTMLAttributes<HTMLDivElement>`, `CardProps extends ComponentProps<'div'>`, `IconButtonProps`, `InputGroupProps`). `TypographyProps<E extends ElementType>` is generic over the rendered element, with a `variantElementMap` giving each style variant its default semantic tag and an `element` prop to override it independently. Hand-written domain types: `NavigationElement` / `NavigationItem` / `NavigationGroup` plus the `isNavigationGroup` / `isNavigationItem` guards (`src/components/Sidebar/types.ts`), `ToastVariant` / `ToastAction` / `ToastOptions`, `Breakpoint`, `ScrollShadowOrientation` / `ScrollShadowVisibility`, and the Stepper types. Nothing here is generated. Full definitions: `src/components/*/index.tsx`.

No environment variables. ## Cross-Feature Dependencies

- **ui → (none)** — leaf package. Zero monorepo workspace dependencies: TypeScript config is vendored as `tsconfig.base.json`, and vitest is configured locally (`vitest.config.ts`). Peer contract (never runtime `dependencies`): `react` `^19`, `react-dom` `^19` (Radix), `tailwindcss` `^3.4` (preset imports `tailwindcss/defaultTheme` / `plugin`), and optional `@types/react` `^19` via `peerDependenciesMeta`. `react` / `react-dom` / `tailwindcss` stay in `devDependencies` only for Storybook and local builds — shipping them as `dependencies` nests a second React under the package and triggers "Invalid hook call" when the consumer is on another 19.x. Published name is `@devart/ui-react`; registry is the Devart Nexus instance (`publishConfig.registry`), asserted on every build by `scripts/verify-dist.mjs` so a typo cannot survive to a tag pipeline.
- **apps/web → ui** — the most heavily imported internal package: 710 subpath imports across 382 files. Also inherits the Tailwind theme via `presets: [preset]` (`@devart/ui-react/tailwind-preset`), the `pressed:` variant, and `tailwindcss-animate` — dropped from `apps/web`'s own `devDependencies` now that the preset supplies it.
- **apps/web → ui (tokens, duplicated)** — `apps/web/src/index.css` keeps its own full copy of the token set inline (inside `@layer base`), rather than `@import`ing `@devart/ui-react/globals.css`; the app decided to keep `index.css` as the single file where its tokens and its own `@layer base` additions live (see `apps/web/SPEC.md`, decision 4). `packages/ui/globals.css` is this package's shipped token file, consumed by Storybook and by external consumers of the published package. The two files are deliberately kept in sync by hand and are currently identical: 231 `:root` + 76 `.dark` custom properties, same values, both legacy-palette-free, both carrying the same geometry/elevation/typography tokens. Every token addition or change is therefore a two-file edit (`apps/web/src/index.css` and `packages/ui/globals.css`); nothing in the build enforces the two staying in sync, so drift surfaces as a wrong pixel rather than a failing build. Separately, and unaffected by the token duplication: `apps/web` consumes the Tailwind preset via `./tailwind-preset` and spreads `contentGlobs` into its own `content` array. The package additionally ships `fonts.css` (self-hosted DM Sans `@font-face` + the four `.woff2` files under `fonts/`) for consumers with no font pipeline of their own, such as Storybook; `apps/web` keeps its own near-identical `@font-face` block rather than importing it, because `index.html` preloads `/fonts/dm-sans-latin-normal.woff2` from the app's own public path.
- **apps/web → ui (DOM contract)** — `apps/web/src/shared/utils/is-modal-open.ts` queries `[data-modal-overlay][data-state="open"]` to suppress the global file-drop overlay and its window-level drop guard while a modal or sheet is open (see `apps/web/SPEC.md`, decision 9). The dependency is a CSS selector, so it is invisible to TypeScript and to the Storybook gate: dropping the attribute, or shipping a new overlay primitive without it, yields a file drop landing behind an open dialog and no error anywhere.
- **web-e2e → ui (indirect)** — Playwright locators bind to primitives' accessible semantics rather than test ids (e.g. `UploadFilePage.ts` matches the `File` component by `role="button"` plus accessible name), so changing a primitive's role or label structure breaks e2e without touching `apps/web`.

## Key Architectural Decisions

1. **Subpath-only exports, no root barrel** — the `./*` wildcard maps directly onto `src/components/*/index.tsx`, so an import names exactly one component directory and pulls in nothing else. There is no `src/index.ts` to keep in sync and no accidental whole-library import; the cost is that non-component modules need an explicit entry (`./cn`, `./use-mobile`) and internal hooks are private by omission.
2. **Legacy palette frozen, then deleted, rather than rewritten in place** — the redesign introduced Design System v2 **additively**: the legacy variables kept their values and their names, and a parallel three-layer palette was added alongside them. Rewriting `--primary`/`--accent`/`--text-*` in place would have re-themed every component in one commit, with no way to review or revert a single component's appearance; freezing them instead let each component migrate in its own ticket while un-migrated ones stayed pixel-identical. That migration is now finished: the frozen block, the `content.*` nesting, and the `text-content-*` class names have been deleted from both `globals.css` and `THEME_COLORS`. What was previously an enforced-by-review convention (nothing in the build rejected `bg-card`) is now a hard build-time miss — a class resolving to a legacy name simply generates no CSS.
3. **Layer-1 primitives are not exposed to Tailwind** — the ramp variables exist in CSS so semantic tokens can reference them, but `THEME_COLORS` omits them deliberately, so no component can write `bg-slate-200` and pin itself to a specific shade instead of a role. Theme switching therefore never requires touching a component.
4. **Component-scoped tokens as the third layer** — `--btn-*`, `--badge-*`, `--toast-*`, `--segctrl-*`, `--tbl-*` exist so a component's entire state recipe (rest / hover / press / disabled, both themes) is expressible as static utility classes with zero conditionals in TSX, and so a designer-driven tweak to one control is a one-line CSS edit per theme rather than a hunt through variant strings. The accepted cost is the width of the token surface and the fact that some of these variables have exactly one consumer.
5. **CVA over conditionals, with one sanctioned exception** — variants must be `cva()` so `VariantProps` stays the typed contract and classes are reusable without rendering; ad-hoc ternaries and string maps are rejected in review. `Toast` is the exception because Sonner is called imperatively and never receives React props.
6. **`pressed:` custom variant instead of `active:` or `data-[state=open]`** — a single registered variant expanding to `&:active`, `&[aria-expanded="true"]`, and `&[aria-expanded="true"]:hover`. It solves two problems at once: a control that opens a menu should keep its pressed fill for as long as the menu is open, not just during mousedown; and the obvious way to express that (`data-[state=open]:`) is unreliable, because wrapping a trigger in a `TooltipTrigger` overwrites `data-state` on the same element while `aria-expanded` survives. The third selector exists so the pressed fill out-specifies a plain `hover:` rule when the cursor is over an already-open trigger.
7. **Preset + `contentGlobs` instead of a spread config object** — a consumer used to import `tailwind.config.ts` directly; that entry is now `tailwind-preset.ts`, exporting a `preset` (`presets: [preset]` in the consumer's own config) plus `contentGlobs`. The split exists because Tailwind v3 presets carry `theme`/`plugins` but never `content` — a preset's own `content` array is silently ignored — so the package cannot ship one config object a consumer merely re-exports; `contentGlobs` is the explicit workaround, giving the consumer absolute globs into the package's `src` (dev) and `dist` (prod) to spread into its own `content`. Format of the public entry: monorepo `exports["./tailwind-preset"]` points at the TypeScript source so Tailwind's jiti (and `pnpm dev`) needs no ui build; `publishConfig.exports` points at compiled `dist/tailwind-preset.js` (+ `.d.ts`) so external consumers never transpile TS from `node_modules`. `tailwind.config.ts` at the package root is Storybook-only and is not part of the public surface — `apps/web` imports the preset and `contentGlobs` directly.
8. **Token file is pure CSS; the consumer owns the Tailwind directives** — `globals.css` dropped its `@tailwind base/components/utilities` and its `@layer components` block; it is now `:root` + `.dark` custom-property declarations only. A consumer `@import`s it after its own three `@tailwind` lines, so Tailwind's preflight/reset runs exactly once no matter how many packages a project pulls tokens from. The trade-off is that the file alone gives a consumer nothing to render against — it must already own a Tailwind pipeline.
9. **Geometry and typography folded into the token system at Tailwind's own default values** — `--radius-*`, `--sidebar-width*`, `--shadow-thumb*` and `--font-sans` are new CSS variables, each seeded with the value Tailwind (or the previously hardcoded `Sidebar/constants.ts`) already used, so adopting them is a visual no-op that only adds an override point. The type scale (`--font-size-*`, `--line-height-*`) follows the same template — seeded at Tailwind's own default values, so re-expressing `theme.extend.fontSize` through them is likewise a visual no-op. `5xl` through `9xl` are omitted: zero call sites in the repo use them, and since Tailwind v3's `theme.extend.fontSize` merges per key, the stock definitions simply remain in effect for those steps — adding one later is a two-line edit. `xxs` and `compact` stay bare strings with no paired line-height, since pairing either would change eight existing call sites; the standalone `leading-*` scale is therefore still not tokenized — only the line-heights Tailwind itself pairs with a font size are. `--font-weight-{light,normal,medium,semibold,bold,extrabold,black}` follow the same seeded-at-defaults rationale, re-expressing `theme.extend.fontWeight` at Tailwind's own values; `thin` and `extralight` are omitted as zero-usage, left at Tailwind's stock defaults via the same per-key merge. `spacing`, `letterSpacing` and z-index remain deliberately out. Breakpoints took a different shape, because a CSS variable cannot appear in a `@media` query and Tailwind resolves `screens` at build time: one TypeScript constant, `BREAKPOINTS` (`src/lib/breakpoints.ts`), feeds `theme.extend.screens`, the `--breakpoint-*` custom properties the preset emits into the base layer, and `use-mobile`'s JS media queries alike. Generating those variables instead of hand-writing them into the two token files is the deliberate part: they are the one token inert at the very place it invites editing, so a third hand-synced copy could contradict the media queries with nothing failing. The lever is the constant — `useIsMobile`, `DateRangePicker` and `SidebarProvider` still take an explicit pixel prop (`breakpoint` / `mobileBreakpoint` / `sheetBreakpoint`) for a consumer that overrides `screens` in its own config.
10. **Storybook is the verification surface; there are no unit tests** — the package ships zero `__tests__` directories despite depending on `vitest` and `@testing-library/react`. Regressions in a declarative class-string recipe are visual, so the gate is Storybook: `@storybook/addon-a11y` and `addon-themes` in the preview, a build-only CI job on every MR touching `packages/ui` (`frontend/gitlab/storybook-pages.yml`), and a manual `pages` deploy from the default branch. The accepted gap is that Tailwind silently drops a class resolving to no theme key, so a misspelled token produces neither a build error nor a test failure — only a wrong pixel.
